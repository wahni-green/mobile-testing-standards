# Lessons Learned — Field Notes from Rollout

[TESTING_ARCHITECTURE.md](TESTING_ARCHITECTURE.md) and [TESTING_BASELINE.md](TESTING_BASELINE.md) are prescriptive — what to build. This file is descriptive — what actually went wrong the first few times a project built it, and the fix. It's written from real Milestone 0/1a/1b rollouts on Flutter + ERPNext projects, generalized past the specific project it came from.

**How to use this:** skim it before starting CI wiring for Patrol E2E (Milestone 1b) or when a scripted suite goes flaky — most of what's here is cheaper to avoid than to rediscover. When a new project turns up a lesson not covered here, add it and open a PR against this repo (see the main [README](README.md)'s "Contributing back").

## CI infrastructure for emulator/simulator E2E

Device-matrix E2E (Patrol, or any real-emulator test) is the flakiest and most CI-resource-hungry layer of the stack. Expect to spend real time here before it's stable — none of this is specific to one project's bad luck.

| Symptom | Root cause | Fix |
|---|---|---|
| Android emulator job randomly loses contact with GitHub ("hosted runner lost communication with the server"), or the emulator's own watchdog reports a hanging QEMU thread | A shared 2-vCPU hosted runner gets starved when Gradle/Kotlin compilation and the emulator boot compete for the same two cores | If a self-hosted runner is available, prefer it for the Android E2E job specifically (it's the heaviest one). Otherwise this is a real resource ceiling, not a config bug — don't keep tuning flags to work around it |
| Android job runs out of disk mid-build | Hosted runners ship with a small root volume; Gradle's cache plus an Android system image plus the Flutter build fills it | Redirect the Gradle cache to a larger mounted volume rather than resizing the root disk. If moving to a self-hosted runner with real disk, this whole class of workaround becomes unnecessary — don't carry hosted-runner-specific disk hacks onto a self-hosted runner "just in case" |
| Emulator boots but the job is still resource-starved even after fixing disk | The emulator runs a real window, GPU attempts, audio, and boot animation by default — pure overhead in CI where nothing ever looks at the screen | Run headless explicitly: no window, software GPU renderer, no snapshot, no audio, no boot animation, cameras disabled at the AVD level (safe to combine with an in-app fake-camera flag, since one fakes hardware and the other fakes app-level camera access — they don't conflict) |
| `/dev/kvm` not accessible, emulator silently falls back to full software emulation and is too slow to finish inside the job timeout | Hardware acceleration needs an explicit udev rule on some runner images, it isn't automatic | Add the KVM udev rule as its own CI step before booting the emulator, per the emulator-runner action's own docs — don't assume KVM "just works" because it works locally |
| `patrol test` (or any CLI that can prompt interactively) hangs forever in CI printing something like "please enter a valid option" | An unpinned CLI version changed its own no-explicit-target behavior from "silently pick one" to "prompt interactively" — fine locally with a TTY, fatal in CI with no stdin | Pin the CLI version. Always pass an explicit device/target flag even when only one device can possibly be booted, so a future behavior change can't reintroduce an interactive prompt silently |
| iOS simulator job fails with "no devices found for the matching requirements" after previously working | Hosted macOS runner images drop older simulator models on every Xcode bump — this recurs, it's not a one-time fix | Check the runner image's current device list before bumping the model, and expect to revisit this again next time it breaks |
| First test in a Patrol/integration_test file times out on `pumpAndSettle` before the test's actual logic even starts | The test framework's default settle timeout is tuned for a warm widget rebuild, not a full cold app mount under real CI load (network, disk, cold caches) | Give the initial app-mount pump a longer explicit timeout than the framework default; apply it everywhere the suite does a cold mount, not just the one file where it was first caught — they're all equally exposed to the same class of slowness |
| A CI-only test-host crash produces an ambiguous result (e.g. exit code inconsistent with the printed pass/fail summary) and console output alone doesn't explain why | Console logs from the test runner don't capture what happened inside the simulator/emulator process itself | Capture verbose test-runner output and upload the platform's own result bundle (e.g. `.xcresult` on iOS) as a build artifact, unconditionally rather than only on failure — an ambiguous "did it even finish" state benefits from the artifact too, and it's cheap to always keep for a short retention window |

## Writing resilient E2E tests

| Problem | Why it happens | Fix |
|---|---|---|
| A test passes in isolation but fails when run after another test in the same suite | Most E2E frameworks run every test file in one shared app process — auth state, local caches, and in-memory session all persist across files just like they would across screens in a real user session | Have each test detect and clear session state it doesn't control for itself (e.g. log out through the real UI if a "logged in" screen is already showing) rather than assuming every test starts from a clean install |
| Suite-wide pass/fail is inconsistent across runs with zero code changes in between, and which specific test fails changes each time | Tests have an implicit dependency on run order (e.g. one test's action is a precondition for another's), and the runner's default ordering (often alphabetical by filename) isn't something the test author chose | If order matters, force it explicitly — a numeric filename prefix is a blunt but reliable lever when the test runner has no built-in ordering config. Treat unexplained run-to-run flips as an ordering bug to fix, not noise to retry past |
| A field or dropdown exists in the widget tree and is found by its key, but the tap/enter-text on it fails as "not hit-testable" | The on-screen keyboard from a previous field is still covering it — the framework found the widget but it's not actually visible/tappable at its current scroll position | Scroll the field into view immediately before interacting with it, don't rely on whatever position an earlier field's auto-focus-scroll happened to leave the list at. Where possible, order the test's interactions to match the screen's actual visual top-to-bottom layout — a scroll that only ever needs to go one direction is far more robust than one that has to reverse direction partway through |
| A tap lands on the wrong element even though the finder text is correct | A plain-text finder matches the *first* occurrence in tree order, and two different fields/controls can legitimately show the same literal string (e.g. a dropdown's currently-selected value matches the exact text also present in an unrelated field) | Prefer widget keys over text finders wherever a collision is even plausible; if using text values as test fixtures, pick values that don't collide with other on-screen text |
| A flow hangs until timeout right after an action that should have completed instantly | The action triggers a native OS-level dialog (location/camera/notification permission) that lives outside the app's widget tree entirely — nothing in the app's own UI can dismiss it, and simulator/emulator-level pre-granted permissions often don't survive a fresh install between test runs | Use the E2E framework's native-dialog APIs to detect and grant/dismiss the permission dialog explicitly in the test, right after the action that triggers it — don't rely on environment-level pre-granting to persist |
| A test written against one account/data state passes once, then fails on every subsequent run against the same account | The screen's behavior branches on server-driven state that changes as a side effect of the test itself (e.g. a once-per-day action, a toggle that flips after use) — the test assumed a fixed happy path, not the actual state machine | Query the same status signal the app itself uses before deciding what the test should expect, and branch the test accordingly (or skip with a clear reason) instead of assuming the first-observed behavior is the only one |

## Cross-checking against the real backend

The core mechanism in [TESTING_ARCHITECTURE.md](TESTING_ARCHITECTURE.md) — assert against the UI *and* the API — only works if the API-side assertion is checking the right thing. In practice:

- **Don't assume every endpoint's response envelope has the same shape.** A REST API with dozens of endpoints often has one whose success payload is keyed differently than the rest (e.g. every list endpoint wraps its payload under one common key, except this one which uses a different key). A cross-check helper that assumes uniformity silently reads `null` and passes-by-vacuous-truth or fails every time, for reasons that have nothing to do with the thing under test. Verify each cross-check against the real model/parsing code the app itself uses for that same call, not against a pattern copied from a neighboring endpoint.
- **A list endpoint's summary shape often doesn't include the field you actually want to assert on.** A "list my recent orders" call frequently returns headline fields only (id, status, total) with no line-item detail — asserting on a nested field that was never in the payload is *structurally* guaranteed to fail (or pass vacuously) regardless of what the backend actually did. Check the real response shape before writing the assertion, and use the dedicated detail/get-single-record call when the summary doesn't carry what's needed.
- **Don't assume a list is sorted newest-first.** Filtering "just take the first entry" to find a just-created record is fragile unless the API contract guarantees ordering — it often doesn't, especially under concurrent writes from other test runs. Scope the query by a reliable filter (e.g. created today, by the known ID) and search rather than trusting position.
- **Mandatory parameters that the app always supplies internally are easy to miss when calling the same endpoint directly from a test.** A required date range, a required linked-record ID, etc. — the app's bloc/service layer may compute and inject these silently, and a hand-written test call that skips them fails with a server-side error that reads like a bug in the endpoint rather than a missing test parameter. Read the app's own calling code before writing a test that calls the same endpoint independently.
- **A byte-stream/file-download endpoint can still return a JSON error body with a 200 status.** Don't gate "did this succeed" on status code alone for binary/bytes-mode responses — check content-type, and treat a JSON content-type on a call that should return bytes as the error path, surfacing the server's real message instead of handing the raw error bytes to the user as if they were the file.

## Debugging methodology

The most expensive lessons from rollout were about *how* to chase down a failing cross-check, not the bugs themselves:

- **Isolate client from backend with the most primitive tool available before theorizing about either.** A raw HTTP call (curl or equivalent) made completely outside the app, the test framework, and any HTTP client wrapper is the fastest way to rule out an entire category of explanation. If the same request/response round-trip reproduces (or doesn't reproduce) the bug outside all of that machinery, most client-side theories are eliminated in one step.
- **Be suspicious of your own timing measurements.** An apparent "N-second delay" observed while manually polling can easily be latency in the *investigation* process itself (separate tool calls, round-trips between checks) rather than a real delay on the backend. Before building a fix around a measured delay (e.g. widening a poll/retry window), re-measure with the check made immediately and back-to-back, not across separate steps.
- **When a suite's result flips between identical runs with no code change, the suite is flaky or order-dependent — full stop.** Don't read the most recent green run as "confirmed fixed" until it's reproduced more than once. A single pass after a fix is a data point, not a conclusion, especially for anything touching device emulation or shared test-account state.
- **Never fix flake or a wrong assertion by deleting or loosening it** (also stated in [TESTING_ARCHITECTURE.md](TESTING_ARCHITECTURE.md)'s tradeoffs). If deep investigation confirms the failure is a real backend bug outside this codebase's control, leave the assertion red/failing on purpose and document why, rather than softening the test to make CI green. A red test that's tracking a real, known, external bug is more valuable than a green one that's stopped checking.
- **Re-check your own root cause even after finding "a" bug.** A fix that makes a symptom disappear isn't necessarily the actual cause — confirm by re-deriving what the *old*, broken behavior would have had to produce, and check that it matches what was actually observed. (Concretely: a wrong response-key read that always returns empty explains a "no matches found" result completely on its own — if five different theories were floated for the same symptom before the actual one-line bug was found, the earlier four were investigating a red herring.)

## General principles

- **Real E2E and contract testing surfaces genuinely dead code.** Writing a test against a bloc/handler that turns out to have no caller anywhere in the app is a signal to delete that code, not to fix it into working — verify there's truly no caller (not just none in the obvious place) before deleting.
- **A contract test only guards what it actually asserts on.** A test that only checks a response's top-level success flag can pass for months while a nested field is silently mapped to the wrong key or missing entirely — the bug only surfaces once something (often a later E2E cross-check) actually reads that specific field. When adding a new assertion, assert on the same field the real consumer (UI, bloc, model) reads, not just "did the call not error."
- **Fixture/test data discovered dynamically (fetched from the API at test time) ages better than hardcoded IDs.** Hardcoded customer/item/record identifiers break the moment the backing environment's data changes; a test that fetches "a valid X" at run time survives environment drift.
- **Business-logic mismatches inside the app can hide behind a testing milestone and are worth flagging even when out of scope to fix there.** E.g. two different code paths independently deciding "does this item have a price" using different underlying fields, so they can disagree — found while making an E2E fixture picker, not the feature itself. Log it as a real product bug rather than working around it silently in test fixtures without a trace.
